# Security Policy

Downpour handles browser session cookies, authentication headers, and signed URLs. A defect
here can expose a user's accounts, so security reports are treated as the highest priority
class of issue in this project.

## Reporting a vulnerability

**Do not open a public issue.**

Use GitLab's private vulnerability reporting on this project, or email
`duongchausky@gmail.com` with `[downpour-security]` in the subject.

Please include: what you found, how to reproduce it, the version or commit, and what an
attacker could achieve. A proof of concept is welcome but not required.

## What to expect

| Stage | Target |
| ----- | ------ |
| Acknowledgement | 72 hours |
| Initial assessment | 7 days |
| Fix or mitigation plan | 30 days for high severity |
| Coordinated disclosure | 90 days by default, negotiable by severity |

Credit is given in the release notes unless you prefer otherwise. There is no bounty
programme — this is an unfunded project, and saying so plainly is better than implying
otherwise.

## Scope

**In scope**

- Anything that leaks cookies, credentials, or signed URLs — including into logs
- Path traversal via `Content-Disposition`, manifests, or IPC input
- Command injection via filenames, manifest values, or FFmpeg arguments
- Native messaging host: memory exhaustion, crash, or unvalidated input reaching the daemon
- IPC socket or named pipe: authentication bypass, privilege issues
- Anything that causes **silent file corruption** — we treat this as a security-class defect
  because the user cannot detect it
- Supply chain: a malicious or compromised dependency we ship

**Out of scope**

- A local attacker already running as the user. They can read the keyring and the files
  directly; nothing inside the process changes that.
- A malicious server serving content the user asked for. Downpour guarantees the bytes are
  delivered faithfully, not that they are safe to run.
- Missing hardening that has no demonstrated impact.
- Reports generated by a scanner with no analysis attached.

## Design boundaries, not bugs

These are deliberate and documented in [`docs/10-security-privacy-legal.md`](docs/10-security-privacy-legal.md)
and [ADR-0008](docs/adr/0008-no-drm-no-mitm.md). Reports asking us to add them will be closed:

- No DRM circumvention.
- No TLS interception, no MITM proxy, no injected root CA.
- No certificate-verification bypass in any build.
- No access-control, rate-limit, or bot-detection evasion.

## Supported versions

Pre-1.0, only the latest release receives fixes.
